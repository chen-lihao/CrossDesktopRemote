# 文件与剪贴板传输协议

## 当前完成边界

阶段 1 已完成协议和 Rust 核心，阶段 2 已完成 macOS/Windows UTF-8 文本剪贴板 MVP。阶段 3 桌面 MVP 已完成显式文件/目录选择、接收目录确认、16 KiB 分片、背压、暂停/恢复/取消、SHA-256、随机 `.cdrpart`、原子落盘和会话内网络断线续传。文件剪贴板、应用重启后续传、20 GB/磁盘满物理门禁及Rust原生数据泵仍未完成。

## 显式文件传输 MVP

- 能力门禁：仅 macOS/Windows 双方声明 `explicit-file-transfer-v1` 后创建文件通道；iPad 和旧客户端不显示入口，也不影响原远控与文本剪贴板。
- 系统选择器：使用 Flutter 官方 `file_selector` 调用 macOS/Windows 原生文件与目录选择器；macOS 只获得用户明确选择内容的沙箱读写权限。
- 接收确认：接收方先查看任务摘要，再主动选择保存目录；接受前不创建任何文件。
- 双角色入口：控制端从远程工具栏打开传输中心；被控端从“共享本机”状态卡打开同一个传输中心。收到请求时被控端显示待确认徽标、内联接收卡和“查看”消息操作，但不会由网络事件自动弹出系统目录选择器。
- 通道：`file-transfer-control` 传输清单、确认、命令与恢复位图；`file-transfer-data` 传输 ordered/reliable 二进制帧。两个通道均独立于视频、输入和文本剪贴板。
- 分片与背压：单条网络消息严格不超过 16 KiB，二进制头占 36 字节；发送缓冲最多保留 8 个网络分片，超限后停止磁盘读取并轮询等待回落。
- 恢复：逻辑恢复块为 256 KiB；网络中断时保留随机 `<target>.<transfer-id>.cdrpart`，重连后先关闭句柄并截断到最后一个完整块，再交换恢复位图。
- 完整性：发送前与接收完成后分别流式计算 SHA-256；摘要一致才在同一目录内原子改名，取消会删除未完成临时文件。
- 路径：拒绝绝对路径、`..`、控制字符、Windows 保留名、符号链接和越界枚举；同名顶层内容自动生成不冲突名称。现有 Dart 预检仍不能完全消除 TOCTOU，生产发布前必须下沉到目录相对/no-follow 原生写入器。
- 调度边界：当前 `flutter_webrtc` 仅向 Dart 暴露 DataChannel，桌面 MVP 由独立应用服务处理有界帧，SHA-256 放在工作 Isolate，不进入 Widget 树。生产目标仍是把磁盘读写和数据泵下沉至 Rust/平台原生层。

## 文本剪贴板 MVP

- 平台入口：macOS 使用 `NSPasteboard.changeCount` 每 250ms 检测变化；Windows 使用 `AddClipboardFormatListener` 和 `WM_CLIPBOARDUPDATE`。
- 会话入口：双方都声明 `text-clipboard-v1` 后，Host 才创建 ordered/reliable `clipboard` DataChannel；旧客户端继续使用原有远控通道。
- 协议过渡：当前 Flutter M1 会话使用与 Protobuf 语义一致的 JSON v1 `hello/offer/request/data/applied`封装；`hello.supportsApplied` 用于旧客户端降级，文件传输接入时再与 Rust/C ABI 的 Protobuf 数据面合并。
- 传输约束：只允许 `text/plain;charset=utf-8`，单条最大 256 KiB，按 9 KiB 原始字节分片，接收端校验连续 offset、声明大小和 SHA-256。
- 隐私约束：建立连接时只记录 baseline，不发送连接前历史；会话日志不记录文本内容。
- 回环抑制：OS revision 去重，远程 revision 防重放，SHA-256 匹配的原生写入回声仅抑制一次，不阻断用户后续重新复制相同文本。
- 方向策略：关闭、双向、控制端→被控端、被控端→控制端；两端各自的发送/接收策略都必须允许。
- 显式粘贴：用户触发远程粘贴时可发布当前本机剪贴板（包括会话建立前的 baseline）；新客户端在被控端原生剪贴板写入后返回 `applied`，控制端最多等待 300ms 再发送系统粘贴快捷键。
- 快捷键语义：控制端只将 `A/C/F/V/X/Z` 视为跨平台主快捷键；Windows `Ctrl` 和 macOS/iPadOS `Command` 按被控系统映射为 Windows `Ctrl` 或 macOS `Command`，其他修饰键保持原始语义。

## 能力协商与兼容

- 本地与远端分别声明 `ClientCapabilities.clipboard` 和 `ClientCapabilities.transfer`。
- 协议主版本必须同为 `1`；次版本取双方较小值。
- 格式、传输类型和限额只取交集，WebRTC 单消息上限强制收敛到 16 KiB。
- 旧客户端缺少新增字段时，剪贴板和文件传输均关闭，但屏幕、输入和既有会话继续工作。
- V1 只选择双方共同支持的 WebRTC。`TransferTransport` 已隔离任务状态机与数据面，未来 QUIC 实现不改变任务 API 和 Protobuf 元数据。

## WebRTC 通道模型

| Lane | 推荐 DataChannel | 可靠性 | 用途 |
| --- | --- | --- | --- |
| `Clipboard` | `clipboard` | ordered + reliable | 格式清单、按需内容请求、小型分块 |
| `Control` | `file-transfer-control` | ordered + reliable | offer、accept/reject、暂停、恢复、取消、进度与恢复位图 |
| `File(0)` | `file-transfer-data` | ordered + reliable | MVP 串行文件二进制分片；后续可按调度增加有限并行流 |

逻辑恢复块默认 256 KiB，每个 WebRTC 消息最多 16 KiB。发送前查询 DataChannel `bufferedAmount`，超过上限时返回 `CDR_ERROR_BACKPRESSURE`，等待原生层的 buffered-amount-low 事件后重试。文件数据优先级低于输入、控制、音频和视频。

## Rust 核心

`transfer-core` 当前提供：

- 明确的任务状态迁移和终态保护。
- 总大小、单文件、条目数、路径深度、逻辑块、线速分片和在途数量限额。
- 跨平台相对路径规范化；拒绝绝对路径、`..`、Windows 设备名、ADS 分隔符和已存在的符号链接路径。
- Manifest 重复路径、总大小和“文件下再放子项”的校验。
- 可序列化的恢复位图、连续进度和缺失范围计算。
- RustCrypto `sha2` 的流式 SHA-256 与最终摘要验证。
- `TransferTransport` trait 和带消息限额、`bufferedAmount` 背压的 `WebRtcTransport`。

路径预检不能单独消除 TOCTOU。后续各平台文件写入器仍必须使用相对目录句柄和 no-follow 语义，把内容先写入随机 `.cdrpart` 文件，完成 SHA-256 校验后再原子重命名。

## C ABI 所有权

`client-ffi/include/crossdesktop_core.h` 暴露不透明 `CdrTransferManager`，支持创建、接受、暂停、恢复、取消、记录进度、开始校验、完成和进度查询/订阅。

- Manager 由创建方销毁，当前要求单线程串行调用。
- 进度和 WebRTC 回调在调用线程同步执行，不得重入 Manager。
- WebRTC send callback 必须在返回前消费或复制 payload，不能保存 Rust 借用指针。
- 回调和 `user_data` 的生命周期由原生调用方保证，替换或销毁 Manager 后不得继续使用。

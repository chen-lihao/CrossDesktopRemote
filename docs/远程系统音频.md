# 远程系统音频

## 产品边界

远程系统音频使用与视频相同的 WebRTC PeerConnection，但作为独立的音频轨道协商和传输。它不属于某个显示器，因此主副屏切换只替换视频轨道，不重建或中断音频轨道。

当前范围：

- macOS 13 及以上被控端：使用 ScreenCaptureKit 采集系统播放声音。
- Windows 11 被控端：使用 WASAPI process loopback 采集当前会话的系统播放声音，并排除本应用进程。
- macOS、Windows、iPadOS 控制端：通过 WebRTC 原生音频设备播放远端声音，并提供本地静音开关。
- 不采集麦克风，不提供双向语音通话，不把 PCM 音频帧送入 Dart。
- DRM/受保护媒体可由操作系统返回静音，应用不得绕过系统保护。

## 用户授权与权限

被控端的“共享本机系统声音”是持久化总开关，默认关闭。关闭时即使对端支持音频，也不会启动原生音频采集。

动态连接码会话只受该总开关控制。可信设备会话还必须满足被控端为该设备授予 `listenSystemAudio` 权限；该权限不包含在默认可信权限中，并与查看屏幕、控制输入、剪贴板和文件权限相互独立。总开关或可信权限任一关闭，音频轨道均不发送媒体。

控制端的静音开关只关闭本机播放，不改变被控端授权、采集开关或另一控制端的策略。会话断开时必须停止原生采集、解除 Sender 轨道并释放 MediaStream。

## 能力协商

音频使用两个方向能力：

- `system-audio-capture-v1`：被控端能够采集系统播放声音。
- `remote-audio-playback-v1`：控制端能够播放远端音频轨道。

双方必须分别声明对应能力后才启动采集。可信会话的能力集合和 `listenSystemAudio` 权限继续参与现有授权摘要及签名 WebRTC Binding，信令服务不能增加权限或替换能力。旧客户端缺少任一能力时只关闭音频，视频、输入、剪贴板和文件传输继续按原协议运行。

## 媒体链路

```text
macOS ScreenCaptureKit / Windows WASAPI process loopback
                         │
                         ▼
              native 48 kHz stereo PCM
                         │
                         ▼
            WebRTC raw audio source / Opus
                         │
              same PeerConnection audio RTP
                         │
                         ▼
          controller native audio output device
```

Windows 采集与 WebRTC 送帧线程解耦，使用 10 ms 音频帧、有界环形缓冲和 100 ms 启动预缓冲，避免 WASAPI 批量回调直接扰动 WebRTC 音频线程。

macOS 不把系统声音伪装成麦克风，也不接入 `AVAudioEngine.inputNode`。ScreenCaptureKit 输出先归一化为 48 kHz、16-bit、双声道 PCM，再使用 ScreenCaptureKit 呈现时钟交给 WebRTC 外部 AudioDeviceModule；WebRTC 负责 10 ms 编码分帧和拥塞控制。不再引入独立 GCD 定时器、预缓冲或欠载补静音，避免两个时钟漂移造成断续、变调和音色失真。该外部设备的输出半部通过系统默认 AudioUnit 播放远端音频，所以同一 Mac 作为控制端时仍能接收 Windows 音频。自动增益、回声消除和降噪均关闭，避免处理系统原声。

macOS 启动采集前必须完成原生运行时握手：后端名为 `screen-capture-kit-external-adm`、协议版本不低于 3、声明 `microphoneFree`、`deliveryMode=capture-clock-render-block` 且 WebRTC 输出帧长为 10 ms。握手不满足时失败关闭，禁止回退到麦克风采集。诊断信息只包含捕获/送入帧数、时钟不连续、转换和送帧失败计数，不包含 PCM 内容。

控制端播放使用进程级租约管理：iPad/iPhone 在首个远程会话开始时将 `AVAudioSession` 设为 `playback + default + mixWithOthers`，并继续使用已通过真机播放验证的 WebRTC AudioEngine。Dart 租约只负责引用计数和播放策略，不能直接停用进程级 `AVAudioSession`；最后一个 PeerConnection 的原生 `dispose` 是唯一音频会话终止所有者。macOS 与 Windows 继续使用系统共享混音输出。因此远程声音与控制端本机声音可同时播放，不启用语音通话模式、不压低其他应用音量。

iOS 固定使用的 WebRTC AudioEngine 可能在内部音频图生命周期中初始化系统输入节点，因此应用必须声明 `NSMicrophoneUsageDescription`，否则系统会在断开阶段直接终止进程。该声明不等于采集麦克风：CrossDesktopRemote 不请求麦克风权限、不创建本地麦克风轨道，也不发送麦克风媒体。若未来希望彻底移除该声明，必须改用具有可复现源码构建和真机验收的播放专用 WebRTC ADM，不能在预编译框架外临时替换音频设备。

音频采集生命周期通过单一串行队列管理。快速开关、会话关闭和启动失败不能并发操作同一个原生采集器；旧 generation 的异步启动结果必须立即停止并释放。控制端断开同样是单一事务：先禁用远端音轨，再执行一次 PeerConnection `dispose`，最后释放 Dart 播放租约；重复关闭请求复用同一个 Future，禁止 `close + dispose + lease deactivate` 三重终止。

## 验收清单

- [x] Flutter 能力、默认权限与设置持久化自动测试。
- [x] Rust 能力协商、权限位和旧客户端降级自动测试。
- [x] macOS Debug 构建、iOS 模拟器构建、Java 信令测试。
- [x] Flutter 对 macOS 外部 ADM 的运行时握手、旧后端失败关闭和 10 ms 帧契约自动测试。
- [x] iOS 播放基线、单次 PeerConnection 终止、租约所有权和隐私声明边界自动测试。
- [ ] Windows 11 + MSVC `/WX` 完成原生编译。
- [ ] Mac → Windows、Windows → Mac、Mac/Windows → iPad 各持续播放 30 分钟，无明显爆音、持续断音或音画漂移。
- [ ] 主副屏往返切换 30 次，音频不中断且不会重复创建音频轨道。
- [ ] 被控端默认不采集；关闭总开关、撤销可信音频权限或断开会话后立即停止采集。
- [ ] 控制端静音/恢复各 30 次，不触发重新协商，不影响视频和输入。
- [ ] 系统睡眠唤醒、默认输出设备切换和音频服务重启后，失败状态可诊断；自动恢复能力在完成目标平台真机验证前不得标记为已验收。
- [ ] 旧客户端连接时无音频，但原有远控能力不回归。

## 当前限制

- Windows 原生编译、WASAPI 设备变化和真实声卡行为只能在 Windows 真机验收。
- macOS ScreenCaptureKit 系统声音要求 macOS 13 及以上，并受屏幕录制权限和系统受保护内容策略约束。
- 当前仓库固定的 WebRTC XCFramework 在 macOS 二进制中提供外部 AudioDeviceModule 实现和工厂入口，但遗漏对应公开头文件；本地声明严格固定到 `144.7559.09` ABI。升级 WebRTC 时必须重新核对头文件/符号并完成三端构建，不允许复用未经验证的声明。
- 当前只实现桌面系统声音下行；麦克风、语音聊天、Android/Linux 被控端音频采集不在本阶段范围。
- 睡眠、声卡热切换或底层音频服务重启后的无缝恢复仍需真机数据决定是否引入平台级重建策略，不能用定时重启采集器掩盖故障。
